# 증권사 자격 증명 암호화 키 로테이션 운영 절차

이 문서는 `docs/agent-tasks/broker-credential-encryption-key-rotation.md`(S7 설계)에서
승인된 결정을 따라 구현된 오프라인 재암호화 배치의 운영 절차다. 실제 Base64 키 값이나
운영 DB 접속 정보는 이 문서 어디에도 적지 않는다 — 모두 로컬 환경변수 또는 운영 비밀
관리 도구에만 있어야 한다.

## 요약

- 대상: `broker_connection_secret_values`(값 단위)와 `broker_accounts`(계좌 단위)에 저장된
  구버전 `encryption_key_version` 행.
- 동작: 평문은 바꾸지 않는다. 저장된 버전 키로 복호화한 뒤 현재 키링 버전
  (`tradeguide.broker.encryption-current-version`)으로 다시 암호화해 "같은 값, 다른 봉투"로
  교체한다.
- 실행 방식: 애플리케이션 기동 시 한 번, 운영자가 명시적으로 켠 프로퍼티가 있을 때만
  실행되는 오프라인 배치다. HTTP 엔드포인트, 스케줄러, 프런트엔드 어디에도 연결하지
  않는다.
- 실행 기록: `broker_key_rotation_runs` 표 하나가 유일한 감사 기록이다. ciphertext·평문·키
  값을 담지 않으므로 그대로 인시던트 문서에 인용해도 안전하다.
- 기본값은 항상 비활성(`run-on-startup: false`)이다. 이 절차를 따르지 않으면 로테이션은
  전혀 실행되지 않는다.

## 사전 준비물 (실행 전 반드시 확인)

1. **새 버전 키를 발급한다.** Base64로 인코딩한 32바이트 AES 키를 새로 만들고, 새 버전
   번호(예: 기존이 1이면 2)를 정한다. 이 키 값은 운영 비밀 관리 도구 또는 배포 파이프라인의
   환경변수로만 전달한다 — 코드, 문서, 로그, 대화 어디에도 남기지 않는다.
2. **기존 버전 키를 절대 지우지 않는다.** 로테이션이 끝난 뒤에도 이전 버전 키를 설정에서
   당장 제거하지 않는다. 다음 한 번의 로테이션 주기 동안 보존해, 문제가 생겼을 때 이전
   버전으로 다시 로테이션(사실상 롤백)할 수 있게 한다(§1 결정 5, 보존 기간은 운영자가
   정한다).
3. **두 버전 키를 모두 애플리케이션에 전달한다.**
   - `BROKER_CREDENTIAL_ENCRYPTION_KEY_V1` — 기존 버전 키(이미 설정돼 있어야 한다).
   - `BROKER_CREDENTIAL_ENCRYPTION_KEY_V2` — 새로 발급한 키.
   - `BROKER_CREDENTIAL_ENCRYPTION_CURRENT_VERSION=2` — 이번 로테이션의 목표 버전. 로테이션은
     항상 "현재 버전"으로만 재암호화하며, 별도 버전을 지정하는 옵션은 없다.
   - 버전 번호와 환경변수 이름은 예시다. 실제 배포의 기존 버전 번호에 맞춰 조정한다.
4. **`run-on-startup`을 켤 때만 배치가 돈다.**
   - `BROKER_CREDENTIAL_ROTATION_RUN_ON_STARTUP=true`
   - 이 값을 켜지 않은 평소 기동에서는 로테이션 코드가 전혀 호출되지 않는다.
5. **배치 크기는 필요하면만 조정한다.** 기본값은 200행/트랜잭션이다
   (`BROKER_CREDENTIAL_ROTATION_BATCH_SIZE`). 임의로 바꾸지 않는다 — 이 값은 별도 승인을
   받은 운영 상수다.
6. **DB와 애플리케이션을 백업 정책에 맞춰 확인한다.** 로테이션은 스키마를 바꾸지 않지만,
   실행 전 최근 백업이 있는지 일반적인 운영 원칙에 따라 확인한다.
7. **이 실행이 진짜 오프라인인지 확인한다.** 이 배치를 실행하는 인스턴스는 사용자 트래픽을
   받지 않는 별도 기동(로컬 셸 또는 배포 파이프라인의 일회성 단계)이어야 한다. 운영
   트래픽을 받는 인스턴스에서 이 플래그를 켜지 않는다.

## 실행 절차

1. 위 사전 준비물 1~6을 모두 환경변수로 설정한 뒤, 애플리케이션을 **한 번** 기동한다(로컬
   셸 또는 배포 파이프라인의 일회성 단계). 기동 시 `BrokerKeyRotationRunner`가
   `run-on-startup`이 켜져 있는지 확인하고, 켜져 있으면 로테이션을 실행한 뒤 애플리케이션은
   평소처럼 계속 기동된 상태로 남는다.
2. 실행이 끝나면 `BROKER_CREDENTIAL_ROTATION_RUN_ON_STARTUP`을 다시 `false`로 되돌린다(또는
   제거한다). 이 값을 켠 채로 남겨 두면 다음 기동에서도 매번 로테이션을 다시 시도한다 —
   대상 행이 없으면 즉시 완료로 끝나므로 위험하지는 않지만, 불필요한 반복이다.
3. `broker_key_rotation_runs` 표에서 방금 실행한 행을 확인한다(가장 최근 `started_at`).
   - `status = COMPLETED`이면 성공이다. `secret_values_processed`/`accounts_processed`가
     각각 `secret_values_total`/`accounts_total`과 일치하는지 확인한다.
   - `status = FAILED_PREFLIGHT`이면 어떤 행도 손대지 않았다. `failure_reason`을 확인한다.
     - `ENCRYPTION_NOT_CONFIGURED`: 키가 하나도 설정되지 않았다. 사전 준비물 3을 다시
       확인한다.
     - `TARGET_KEY_MISSING`: 목표 버전(현재 버전) 키가 목록에 없다. 사전 준비물 3의
       버전·환경변수 이름을 다시 확인한다.
     - `MISSING_SOURCE_KEY`: 실제로 재암호화가 필요한 구버전 중 키가 없는 버전이 있다.
       그 구버전 키를 다시 추가한다 — "쓰기만 새 키로, 읽기는 실패"인 절반 상태를 막기
       위한 의도된 거부다.
     - `SAMPLE_ROUNDTRIP_MISMATCH`: 대상 행 중 표본 하나를 복호화 → 재암호화 → 복호화한
       결과가 원래 값과 달랐다. 키 값 자체(오타, 잘못된 인코딩)를 다시 확인한다.
     - `ANOTHER_ROTATION_IN_PROGRESS`: 이미 `IN_PROGRESS` 실행이 있다. 아래 "중단 후 재개"
       절차를 따른다.
   - `status = IN_PROGRESS`로 남아 있으면(완료되지 못하고 끝났다는 뜻) 아래 "중단 후 재개"
     절차를 따른다.

## 중단 후 재개

애플리케이션이 배치 도중 죽거나(배포 재시작, 장애) 영구 손상된 행 때문에 더 진전이 없어
`status = IN_PROGRESS`로 남을 수 있다. 자동 재시작은 하지 않는다 — 반드시 운영자가 원인을
확인한 뒤 아래 중 하나를 명시적으로 선택한다.

- **이어서 실행한다.** 원인(예: 빠진 키)을 고친 뒤, 사전 준비물을 그대로 유지한 채
  `BROKER_CREDENTIAL_ROTATION_RESUME_IN_PROGRESS=true`를 추가로 설정하고 다시 기동한다.
  같은 실행(run) 행을 이어서 진행하며, 이미 처리한 행은 다시 건드리지 않는다(조건부
  UPDATE와 버전 필터가 멱등성을 보장한다). 재개 후에는 이 값도 다시 꺼 둔다.
- **포기하고 새로 시작하기로 한다.** 진행 중인 실행이 더 이상 유효하지 않다고 판단되면,
  운영자가 직접 그 행의 `status`를 `ABORTED`로 갱신한다(애플리케이션이 제공하는 별도
  명령은 없다 — 이 슬라이스는 관리자용 HTTP 표면을 두지 않는다는 원칙을 따른다). 이후
  `run-on-startup`을 다시 켜면 새 실행이 시작된다.

`secret_values_failed`/`accounts_failed`가 0보다 크면(영구 손상 행이 있으면) 이어서
실행해도 그 행은 계속 실패로 집계된다. 근본 원인(손상된 ciphertext 등)을 먼저 조사한다.

## 실행 후 확인

- `broker_key_rotation_runs.status = COMPLETED`이고 실패·스킵이 0인지 확인한다.
- 스킵(`secret_values_skipped`/`accounts_skipped` > 0)은 실패가 아니다. 로테이션 배치가
  읽은 시점과 조건부 UPDATE를 시도한 시점 사이에 사용자가 자격 증명을 교체했거나 계좌가
  재검증된 경우다. 그 행은 이미 최신 키로 저장돼 있으므로 다음 로테이션 실행에서 자연히
  다시 대상이 되면 그때 처리된다.
- 애플리케이션이 평소처럼 자격 증명을 복호화·암호화하는지(연결 검증, 보유 종목 조회 등
  기존 기능) 확인한다.

## 하지 않는 것

- 이 절차는 이전 버전 키를 삭제하지 않는다. 별도 결정과 보존 기간이 지난 뒤에만 수동으로
  제거한다.
- 이 절차는 `broker_connection_secrets`(V17 이전의 옛 표)를 드롭하지 않는다. 그 표는
  애플리케이션이 이미 읽거나 쓰지 않으며, 드롭 여부는 별도 마이그레이션으로 결정한다.
- 이 절차는 증권사 API를 호출하지 않는다.
- 이 절차는 회원에게 어떤 형태로도 노출되지 않는다.
