# 장전 가이드 입력 근거 연결 순서

## 현재 구현

- `PremarketGuideInputAudit`는 가이드별 제공자, 기록 시각, 미검증 사유를 보존한다. 수신 시각과 입력 해시는 아직 비워 둔다.
- `CompletedWeeklyCandleCache`는 최초 로드가 애플리케이션에서 끝난 시각을 캔들과 함께 보존한다. 캐시 적중 시 시각을 새로 만들지 않는다. 이 시각은 거래소의 공표 시각이나 제공자 원본 응답 시각이 아니다.
- 토스증권 캔들 캐시는 포트폴리오별로 분리한다. 공개 시세 제공자 캐시는 포트폴리오 간 공유하되, 자산별 근거는 해당 가이드 스냅샷에 별도로 저장한다.
- 토스 일봉 페이지가 겹치면 날짜별로 한 건만 남긴다. 같은 날짜의 OHLCV가 충돌하거나 페이지 커서·날짜가 진행하지 않으면 조회 실패로 처리해 주봉 거래량과 근거 해시가 잘못 계산되지 않게 한다. 이 검증은 원본 수신 시각의 보존을 대신하지 않는다.
- `PremarketGuideService`는 실제 가이드에 포함된 자산에 대해 캐시의 **완료된 주봉** 기준일이 가이드의 기준일과 일치할 때만 `premarket_guide_candle_evidence`에 제공자·로드 완료 시각·캔들 수·SHA-256을 저장한다. 강제 재생성 시 같은 자산의 근거를 갱신하고 사라진 자산은 제거한다.
- 토스 캔들 응답은 각 HTTP 페이지의 본문 수신 완료 시각을 별도 목록으로 보존한다. Twelve Data는 단일 HTTP 응답의 수신 완료 시각을 보존한다. 가이드 종목의 근거에 수신 순서대로 저장되며 캐시 적중 시 새 시각을 만들지 않는다. 토스의 `adjusted_requested=true`는 요청의 `adjusted=true` 파라미터를 뜻할 뿐, 제공자 가격이 실제로 어떤 기업행위로 조정됐는지를 검증한 결과가 아니다. Twelve Data는 조정 여부를 명시적으로 요청하지 않으므로 `adjusted_requested`가 비어 있다. 기존 스냅샷과 관측을 지원하지 않는 제공자의 수신 근거도 비어 있다.
- 자산별 캔들 근거는 전체 가이드 입력의 일부다. 보유 원장·후보군·위험 설정 버전과 공급자 조정 정책은 아직 고정되지 않았으므로 `PremarketGuideInputAudit.inputSha256`은 비어 있고 UI의 `입력 근거 미검증` 상태도 유지한다.
- 가이드에 포함된 종목의 캔들 근거가 누락되거나 기준일·제공자가 일치하지 않으면 감사 기록의 `missing_reasons`에 `CANDLE_EVIDENCE_INCOMPLETE`를 추가한다. 강제 재생성 시 이전 근거가 새 가이드에 남지 않는지도 검증한다. 이 사유가 없더라도 전체 입력이 검증된 것은 아니다.

## 다음 연결 단위

1. 공급자별 실제 가격 조정 정책과 기업행위 반영 여부를 별도 계보로 검증한다. 현재는 HTTP 수신 완료 시각과 토스의 조정 요청값까지만 연결됐다.
2. 보유 원장 버전·후보/위험 설정 버전을 함께 고정한 뒤 가이드 전체 입력 해시를 산출한다. 일부만 있으면 전체 입력 해시를 기록하지 않는다.
3. 부분 실패, 제공자 변경, 회원·포트폴리오 격리, 과거 가이드 재생 테스트를 통과한 뒤에만 감사 상태를 상향한다. 수익성 검증과 주문 가능성 검증은 별도다.

자산별 로드 완료 시각을 기존 감사 테이블의 `response_received_at`에 그대로 복사하지 않는다. 여러 자산과 캐시가 섞일 때 단일 시각은 입력 전체의 계보를 설명하지 못한다.

## 관측: Toss 캔들 커서의 이력 끝 동작 (2026-09-23)

작업 계약 `docs/agent-tasks/toss-candle-cursor-end-of-history-20260923.md`의 1단계 결과다.

- 관측 시각: 2026-09-23 11:42 KST. 앱을 끈 상태에서 사용자가 로컬 관측 도구(`build/toss-cursor-probe/probe.py`, 저장소 미포함)로 실행했다.
- 요청: `GET /api/v1/candles`, `interval=1d`, `adjusted=true`, 페이지당 최대 200개. 앱과 같이 목표 737개(주봉 101개용 일봉)까지 `count = min(200, 737 - 수집 수)`로 요청했다.
- 날짜는 앱과 같은 방식(`OffsetDateTime.toLocalDate`)으로 해석했다. 토큰·커서 원문·응답 본문은 기록하지 않았다.

| 종목 | 페이지 | 마지막 페이지 요청/반환 | 마지막 `nextBefore` | 고유 거래일 | 범위 | 앱 동작 |
|---|---|---|---|---|---|---|
| SOXL (대조군) | 4 | 137 / 137 | 새 값 | 737 | 2023-10-16 ~ 2026-09-23 | 목표 개수 도달로 정상 종료 (이력 끝 미도달) |
| IBIT | 4 | 137 / 77 | `null` | 677 | 2024-01-11 ~ 2026-09-23 | 이력 끝, 정상 종료 |
| CRCL | 2 | 200 / 127 | `null` | 327 | 2025-06-05 ~ 2026-09-23 | 이력 끝, 정상 종료 |

- 모든 페이지가 HTTP 200이었고, 페이지 사이에 겹치는 날짜는 없었다. 커서 반복이나 새 날짜 없는 페이지는 나오지 않았다.
- 이력 끝은 **요청보다 적은 캔들과 `nextBefore=null`을 함께 반환**하는 형태다. 빈 페이지를 한 번 더 주지 않는다. 판정 표의 첫 행("빈 페이지 또는 `nextBefore` null/blank")에 해당하므로 `41ec765`의 커서 반복·새 날짜 없음 실패 처리는 유지한다.
- 두 종목의 첫 거래일은 알려진 상장일(IBIT 2024-01-11, CRCL 2025-06-05)과 일치했다.

### 관측 한계와 별도 확인 사항

- US 종목 3개, 한 시점의 관측이다. 국내 종목과 다른 시점의 동작은 확인하지 않았다.
- 이력 끝 동작과 별개로, 앱은 완료 주봉이 101개(약 2년) 미만이면 `aggregateWeekly`에서 "주봉 개수 부족"으로 조회 실패 처리한다. CRCL(약 68주)은 커서와 무관하게 이 기준으로 조회 불가가 된다. 이는 기존 설계(40주 이동평균 이력 확보)이며 이번 작업 범위가 아니다.
- US 정규장 개장 전인 11:42 KST에 `2026-09-23` 일봉이 이미 존재했다. 토스 주간거래 등 당일 진행 중 캔들일 가능성이 있으나 확인하지 않았다. 주봉 계산은 `CompletedWeeklyCandleFilter`가 진행 중인 주를 제외하므로 영향은 제한적이지만, 일봉을 직접 쓰는 기능이 생기면 별도로 확인해야 한다.
