## 1. 개요 및 검토 환경

### 1.1 검토 목적 및 배경
본 문서는 Trade Guide의 핵심 기능 중 하나인 **증권사 연동(계좌 등록, 연결 확인, 보유 스냅샷, 개시 잔고 승인, 주문 이력 스테이징 및 원장 반영)**과 이와 연계된 주요 화면(`/broker-accounts`, `/settings`, `/holdings`, `/transactions/new`, `/strategy-guides`)의 정보 구조(IA), 사용자 작업 흐름, 피드백 공간, 모바일 반응형 결함 및 195건 이상의 대량 주문 미리보기 처리 정책을 종합적으로 감사하고, 현 API로 즉시 해결 가능한 P0/P1 개선안과 중장기 백엔드 협업 과제를 제시한다.

### 1.2 실제 브라우저 검증 환경 및 정량 지표
- **검증 도구**: Google Chrome Headless (DevTools Protocol CDP) 기반 실측 스크립트 실행
- **검증 뷰포트**:
  - **모바일**: 360px × 800px (기준 기기: 소형 스마트폰)
  - **태블릿**: 768px × 1024px (기준 기기: iPad Mini / 세로 모드 태블릿)
  - **데스크톱**: 1280px × 800px (기준 기기: 일반 랩톱/데스크톱)
- **주요 실측 정량 데이터 (`/broker-accounts` Run #3, 195건 기준)**:
  - **데스크톱 (1280px)**: 총 DOM 노드 **5,599개**, 전체 페이지 높이 **34,860px**, 주문 카드 목록 높이 **27,485px**.
  - **모바일 (360px)**: 총 DOM 노드 **5,599개**, 전체 페이지 높이 **61,157px**, 주문 카드 목록 높이 **51,968px**.
  - **360px 모바일 가로 넘침(Horizontal Overflow)**: 총 **118개 카드**에서 **235개 요소**가 뷰포트 우측(360px)을 초과하여 363px까지 침범 실측 확인.

## 3. 5대 핵심 영역 상세 평가

### (1) 설정(`/settings`)과 연동 계좌(`/broker-accounts`)의 정보 구조 (IA)

1. **설정 화면 내 '모니터링 데이터' 혼재 문제**:
   - `/settings` 페이지는 본래 "위험 한도(손실율/노출율)"와 "시장 데이터 제공자 선호도"를 설정하는 환경설정 화면임.
   - 하지만 현재 화면 하단에 `CURRENT ALLOCATION - 보유 종목 비중 (PortfolioExposureList)` 섹션이 배치되어 있음.
   - 종목별 현재 평가 비중과 초과 여부를 실시간 조회하는 모니터링 성격의 블록이 설정 폼 바로 아래에 위치하여, "내가 설정을 바꾸는 곳인가, 자산 현황을 보는 곳인가?"라는 멘탈 모델 혼선을 초래함.
2. **연동 계좌(`/broker-accounts`)의 권한 계층 혼재 (Member vs Portfolio)**:
   - 페이지 헤더는 `PORTFOLIO 1`로 포트폴리오 스코프를 명시하고 있음.
   - 그러나 1단계 `BrokerConnectionSection`은 **회원 전체(Member-level)**의 토스증권 API Key/Secret 등록 및 연결 목록 관리임.
   - 2단계부터 6단계는 **해당 포트폴리오(Portfolio-level)**에 대한 계좌 매핑, 스냅샷 갱신, 개시 잔고 승인, 주문 이력 원장 반영임.
   - 동일 화면 안에서 회원 단위 관리(자격 증명)와 포트폴리오 단위 원장 작업이 수직으로 결합되어 있어, 추후 포트폴리오가 2개 이상인 회원은 "포트폴리오 2로 바꿨는데 왜 1단계 증권사 키는 그대로 보이는가?"라는 혼란을 겪게 됨.
3. **고립된 섬(Silo) 형태의 페이지 간 단절**:
   - **`/settings` → `/broker-accounts` 단절**: 설정의 "시장 데이터 제공자"에서 토스증권을 선택하려 할 때 `requiresBrokerConnection` 안내 문구("증권 계좌 연결 필요")만 노출되고, 연동 계좌 화면으로 이동하는 링크나 액션 버튼이 전혀 없음.
   - **`/transactions/new` → `/broker-accounts` 단절**: 수동 매매 등록 화면에 진입한 사용자는 수십 건의 과거 매매를 손으로 직접 입력해야 하는지, 증권사에서 가져올 수 있는지 알 수 없음. "증권사 계좌 연동을 통해 과거 체결 내역을 한 번에 가져올 수 있습니다" 안내 배너가 필요함.
   - **`/broker-accounts` → `/holdings` 단절**: 주문 이력이나 개시 잔고를 원장에 반영한 직후, "반영된 내역 확인하기" 버튼이 없어 사용자가 상단 내비게이션을 찾아 직접 눌러야 함.

### (2) 계좌 등록→확인→선택→스냅샷→개시 잔고→주문 이력 흐름 (Account Lifecycle Flow)

현재 구현된 6단계 흐름은 시스템의 안전 원칙(읽기 전용 조회, 임의 매매 주문 금지, 대조 실패 시 반영 차단)을 훌륭히 준수하고 있으나, 사용자 경험 관점에서 다음과 같은 단절과 치명적 오류가 존재함.

1. **[P0 결함] `/holdings` 화면에서 `BROKER_ORDER_HISTORY` 출처 왜곡 및 409 충돌 오류**:
   - **현황**: 프론트엔드 `TradeTransactionSource` 타입 정의(`frontend/src/types/tradeTransaction.ts:5`)에 백엔드의 `BROKER_ORDER_HISTORY` 열거형이 누락되어 있음 (`"MANUAL" | "BROKER_OPENING_BALANCE"`만 정의).
   - **결과 1**: `TransactionHistoryList.tsx:47`에서 매핑 라벨이 없어 기본값인 **"직접 등록"**으로 화면에 둔갑함.
   - **결과 2**: 직접 등록으로 인식되므로 우측에 **[삭제] 버튼**이 그대로 노출됨.
   - **결과 3**: 사용자가 [삭제]를 누르면 백엔드 `TradeTransactionService`가 `TradeTransactionProtectedException` (409 Conflict, "증권사 주문 이력으로 생성된 매매 기록은 일반 매매 삭제 API로 지울 수 없습니다")을 발생시키며 빨간 오류 박스가 뜸.
   - **올바른 UX**: 증권사 주문 이력 출처(`BROKER_ORDER_HISTORY`)를 명확한 배지로 표시하고, 일반 삭제 버튼 대신 `/broker-accounts`의 해당 실행 상세로 이동하여 안전하게 "원장 반영 취소(Revoke)"를 수행하도록 안내해야 함.
2. **1단계-2단계 간 실시간 반응성 지연**:
   - 1단계에서 자격 증명을 등록하고 `연결 확인`을 마쳐 `VERIFIED` 상태가 되어도, 2단계의 `getBrokerLinkCandidates` 결과가 즉시 연동되지 않고 사용자가 2단계의 "계좌 목록 새로고침" 버튼을 눌러야 후보 목록이 나타나는 마찰 발생.
3. **개시 잔고 기준점(Baseline)과 주문 이력 스테이징 간의 시각적 혼선**:
   - 증권사 주문 이력을 조회하면 개시 잔고 기준일 이전의 주문도 `STAGED` 상태로 함께 수집됨.
   - 화면에서는 `반영 적격` 칩과 `개시 잔고 이전 (원장 제외)` 칩이 같은 목록에 뒤섞여 나타남.
   - 사용자는 "원장에 들어가지도 않을 이전 주문이 왜 후보 목록에 수십 건씩 떠 있는가?" 의문을 갖게 됨.

### (3) 성공·오류 메시지 공간과 버튼 계층 (Feedback & Button Hierarchy)

1. **메시지 삽입에 따른 레이아웃 이동 (CLS - Cumulative Layout Shift)**:
   - 폼 제출 시 `<p className="form-error-message">`나 `<p className="form-success-message">`가 DOM에 동적으로 추가/제거되면서 아래쪽 버튼과 섹션들이 40~50px씩 아래로 덜컥거림.
   - 특히 모바일 뷰포트에서 버튼을 누르는 순간 메시지가 삽입되며 터치 위치가 어긋나는 현상 발생.
2. **메시지 수명 주기(Lifecycle) 관리 부재**:
   - 성공 메시지("위험 한도를 저장했습니다", "토스증권 연결을 저장했습니다")가 다른 액션을 하기 전까지 영구적으로 남아있음.
   - 사용자가 폼 입력을 수정하는 중에도 과거의 "저장 성공" 메시지가 계속 떠 있어 현재 입력값이 저장된 상태인지 혼동 유발.
3. **버튼 시각적 위계(Visual Hierarchy) 과열**:
   - `/broker-accounts` 한 화면 안에 초록색 강조 버튼(`.primary-button`)이 과도하게 많음:
     - 1단계: "토스증권 연결 저장" (Primary)
     - 6단계: "주문 이력 조회 및 미리보기 생성" (Primary)
     - 6단계: "확인 및 매매 원장 반영" (Primary)
   - 실제로 가장 중요하고 신중해야 할 액션인 **"매매 원장 최종 반영 승인"**과 단순 조회 액션인 **"미리보기 생성"**의 시각적 무게감이 동일하여 사용자가 단계의 경중을 직관적으로 인지하기 어려움.

### (4) 모바일 가로 넘침 및 반응형 규칙 (Mobile 360px Overflow)

1. **`.external-order-id` 오버플로우 (363px)**:
   - 본 보고서 2.1절에서 실측된 바와 같이, 66자리 해시가 줄바꿈되지 않고 304px의 고정 너비를 차지하여 우측으로 3px 돌출됨.
2. **상단 내비게이션 5열 그리드 버그**:

3. **대조 테이블(`.reconciliation-table`)의 모바일 탐색성**:
   - 종목, 시뮬레이션 수량, 스냅샷 수량, 수량 차이 4개 컬럼을 가진 표가 모바일에서 가로 스크롤로 제공되나, 스크롤 가능하다는 시각적 단서(우측 페이드 그라디언트 등)가 없어 마지막 "수량 차이" 컬럼의 존재를 놓칠 위험이 있음.

### (5) 대량 주문 미리보기(195건)의 페이지네이션/필터/접기 정책 평가

Run #3의 실측 결과(205건 조회, 188건 스테이징, 7건 미체결, 10건 미지원 통화 등 총 195건 항목)를 바탕으로 대량 목록 처리 정책을 평가함.

1. **현재 정책의 한계**:
   - **무제한 플랫 리스트 (Unpaginated Flat List)**:
     - 백엔드가 195건을 한 번에 내려주고, 프론트엔드가 이를 195개의 복잡한 카드(배지 5~6개, 수량, 단가, 총액, 시각, 식별자 해시 등 포함)로 즉시 렌더링함.
     - 결과: DOM 노드 5,599개, 모바일 높이 61,157px 발생.
   - **핵심 정보의 가려짐 (Loss of Hierarchy)**:
     - 주문 이력 연동에서 사용자가 가장 먼저 판단해야 할 핵심 정보는 **(1) 스테이징 분류 요약 지표(후보 몇 건, 제외 몇 건), (2) 보유 대조(Reconciliation) 결과(수량 일치 여부)**임.
     - 현재 구조에서는 195개의 거대한 카드 목록이 화면의 90% 이상을 점유하여, 정작 중요한 대조 결과와 승인 버튼을 탐색하는 데 방해가 됨.
2. **필터(Filter) 및 검색 한계**:
   - 현재 `전체`, `반영 후보`, `주의·경고`, `제외·보류` 4가지 상태 필터 칩만 제공됨.
   - 188건의 반영 후보 중 특정 종목(예: `SOXL` 또는 `TSLA`)의 체결 내역만 골라서 확인하거나 검증할 수 있는 **종목 티커(Ticker) 검색 수단이 전무**함.
3. **권고 정책 (P0/P1 채택안)**:
   - **클라이언트 가상 페이징 (Client Chunking) — P0 즉시 적용**:
     - 현 백엔드 API 계약을 변경하지 않고, 프론트엔드에서 20건 단위로 기본 렌더링하고 하단에 `[20건 더 보기 (남은 175건)]` 버튼을 제공.
     - 초기 렌더링 DOM 노드가 5,600개에서 800개 수준으로 85% 감소하며, 모바일 페이지 높이가 61,000px에서 2,500px 수준으로 정상화됨.
   - **주문 상세 목록 기본 접기(Accordion / Collapsible) — P1**:
     - 주문 상세 목록 섹션을 기본적으로 "접힘(Collapsed)" 상태로 제공하거나, 대조가 `MATCHED`인 경우 "요약 뷰"를 기본으로 보여주고 `[주문 상세 195건 펼쳐보기]` 토글을 제공.
     - 대조가 `MISMATCHED`이거나 경고 항목이 있을 때만 자동으로 `주의·경고` 필터가 선택된 상태로 상세 목록을 펼쳐주는 스마트 뷰(Smart View) 적용 권고.
   - **종목 검색 필터 입력창 추가 — P1**:
     - 필터 칩 우측에 미니 티커 검색창(예: `SOXL`)을 두어 대량 목록 중 특정 종목만 즉시 필터링 가능하도록 지원.

### 4.3 백엔드 계약 변경이 필요한 항목 (Backend Contract Evolution)

1. **[BE-1] 대량 주문 상세 분할 조회 API (`GET .../broker-order-imports/{runId}/items?page=0&size=50`)**:
   - **배경**: 현재는 `BrokerOrderImportRunDetailResponse` 하나에 `run`, `items`, `reconciliation`이 모두 포함되어 반환됨.
   - **필요성**: 수천 건 단위의 1년 치 거래 내역을 조회할 경우 단일 JSON 페이로드가 수 MB에 달할 수 있음.
   - **제안**: `GET .../broker-order-imports/{runId}`는 요약(`run`)과 대조 결과(`reconciliation`)만 빠르게 반환하고, 상세 목록(`items`)은 페이징 파라미터(`page`, `size`, `status`)를 받는 서브 리소스 엔드포인트로 분리.
2. **[BE-2] 매매 기록 단건 삭제 시 에러 응답에 연동 실행 ID 포함 (`TradeTransactionProtectedException`)**:
   - **배경**: 현재 매매 기록 삭제 API(`DELETE .../transactions/{id}`)는 증권사 출처 데이터에 대해 409 에러 메시지만 반환함.
   - **제안**: 409 에러 응답 body에 해당 매매 기록을 생성한 원본 실행 ID(`brokerOrderImportRunId` 또는 `brokerHoldingImportId`)를 반환하여, 프론트엔드가 즉시 해당 연동 실행 상세 URL(`/broker-accounts#run-{runId}`)로 이동할 수 있는 링크를 띄울 수 있도록 지원.
3. **[BE-3] 회원 단위 자격 증명(`BrokerConnection`)과 포트폴리오 단위 연결(`PortfolioBrokerLink`)의 도메인 API 명확화**:
   - 다중 포트폴리오 확장 시, 하나의 토스증권 연결을 여러 포트폴리오가 공유할 때의 충돌 방지 정책(예: 동일 계좌 중복 원장 반영 차단 등)을 API 계약 레벨에서 정립.

### 4.4 채택 권고안과 비채택 사유 (Adopted vs Rejected Proposals)

#### [채택 권고안]
1. **클라이언트 20건 청크 페이징 (P0-4)**:
   - 현 API 계약을 일체 건드리지 않으면서도 DOM 노드를 85% 감축하고 모바일 61,000px 스크롤 재앙을 즉시 해결할 수 있는 가장 비용 효율적인 방안임.
2. **`/holdings` 화면의 `BROKER_ORDER_HISTORY` 안전 가드 (P0-1)**:
   - 사용자가 삭제 버튼을 눌러 409 에러를 마주하는 불쾌한 경험을 원천 차단하고 시스템 신뢰를 보호함.
3. **360px 오버플로우 및 모바일 5열 그리드 수정 (P0-2, P0-3)**:
   - CSS 몇 줄 수정만으로 모바일 사용성을 표준 수준으로 끌어올릴 수 있는 필수 과제임.
4. **주요 화면 간 크로스 링킹 (P1-3, P1-4)**:
   - 고립된 페이지들을 유기적인 자산 관리 여정으로 연결함.

#### [비채택 사유 (Non-Adopted Proposals)]
1. **[비채택] 주문 상세 목록에서 사용자가 체크박스로 원하는 주문만 골라서 부분 승인하는 기능**:
   - **비채택 사유**: Trade Guide의 증권사 주문 이력 승인은 **"재생 검증(Reconciliation Replay)"을 통해 전체 주문을 적용했을 때 최종 보유 수량과 스냅샷이 일치하는지(`MATCHED`)**를 유일한 안전망으로 삼음. 사용자가 임의로 중간 매수/매도 몇 건을 제외하고 승인하면, 과거 매도 시점에 보유 수량이 부족해지는 `REPLAY_FAILED`나 원장 수량 불일치가 필연적으로 발생하여 원장의 수학적 무결성이 영구히 파괴됨. 따라서 승인은 반드시 "실행 단위 전체 승인"이어야 함.
2. **[비채택] 프론트엔드에서 증권사로 실제 예약 주문을 전송하는 기능**:
   - **비채택 사유**: Trade Guide의 핵심 설계 원칙("자동 매매 도구가 아니며 증권사로 실제 주문을 절대 내지 않음", `AGENTS.md`)에 정면으로 위배됨. 서비스는 의사결정 지원 및 내부 매매 기록(원장) 관리에만 집중해야 함.
3. **[비채택] 백엔드 `getRun(runId)` 상세 응답에서 대조(`reconciliation`) 블록을 제거하거나 별도 호출로 분리하는 안**:
   - **비채택 사유**: `BrokerOrderImportRunDetailResponse`의 설계 원칙대로, 대조는 승인 전 건너뛰어서는 안 되는 유일한 안전장치이므로 실행 상세를 불러올 때 원자적으로 함께 전달되어야 안전함.
