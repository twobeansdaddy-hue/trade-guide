# 웹 MVP 디자인 검토

작업 계약: `docs/agent-tasks/claude-web-mvp-design-review.md` · 작업 모드 `design` · 브랜치 `design/web-mvp-review`

## 이 문서의 지위

이 문서는 **디자인 제안**이다. 채택된 제품 결정이 아니다. 여기의 어떤 항목도
Codex가 API 계약·접근성·Flutter 호환 경계를 검토하고 사용자가 수락하기 전에는
구현 요구사항이나 제품 정책으로 취급하지 않는다
(`docs/AI_COLLABORATION_POLICY.md` 24-26행).

투자 규칙, 자동 주문, 지정가·목표가·손절가, 주문 수량 산식, 증권사 연동은
이 검토의 범위가 아니며 어떤 값도 새로 제안하지 않는다.

## 1. 현재 상태 평가

### 1-1. 채택된 설계와의 대조

`docs/design/WEB_MVP_DESIGN.md`가 확정한 구조는 대부분 구현되었다.

| 채택 항목 | 구현 상태 |
| --- | --- |
| `/`, `/holdings`, `/strategy-guides`, `/settings` 4개 URL | 구현됨 (`App.tsx`) |
| 데스크톱 좌측 내비 · 모바일 상단 가로 내비 | 구현됨 (`App.css` 363-397, 853-855) |
| 표(데스크톱) / 카드(모바일) 이중 렌더 | 구현됨 (`HoldingValuationList`) |
| 보유·후보 가이드 분리 + 조회 불가 목록 | 구현됨 (`StrategyGuidesPage`, `StrategyGuideList`) |
| `tabular-nums` 적용 | 구현됨 |
| `SELL`=매도 검토, `REDUCE`=비중 축소 검토 | 구현됨 (`StrategyGuideList.tsx:4`) |
| `referencePrice`를 `기준 가격`으로만 표기 | 구현됨 |
| 포트폴리오 없는 회원에게 생성 폼 우선 | 구현됨 (`AppLayout.tsx:47`) |
| 종목 카탈로그 검색 + 없을 때 직접 입력 | 구현됨 (`AssetSearchInput`) |
| `VITE_LOCAL_MEMBER_ID` / `GET /api/auth/me` 분기 | 구현됨 (`PortfolioProvider.tsx:8-24`) |

시각 언어도 실제로 운영형 금융 제품으로 읽힌다. 청록 계열 단일 강조색(`#167568`),
중성 배경(`#f5f7f8`)과 흰 표면, 적색 위험, 호박색 조회 불가, 텍스트 라벨을 동반한
상태 배지는 일관적이다. 가상 차트나 장식 카드를 넣지 않은 판단도 유지되고 있다.

### 1-2. 핵심 문제

구조는 갖춰졌으나, **처음 쓰는 사용자와 실패 상황에서 화면이 무너진다.**

1. 새 포트폴리오를 만든 직후 대시보드와 설정에 빨간 오류가 뜬다. 위험 한도가
   아직 없는 정상 상태를 오류로 표시한다.
2. 조회가 실패하면 브라우저 새로고침 말고는 복구 수단이 없다. 재시도 버튼이 없다.
3. 포트폴리오를 바꾸면 이전 포트폴리오의 금액이 화면에 남은 채로 새 데이터가 덮인다.
4. 데이터를 넣는 유일한 경로인 매매 기록 등록이 내비게이션에 없다.

1~3은 금액을 다루는 화면에서 신뢰를 직접 깎는다. 이 네 가지가 P0의 근거다.

## 2. P0 — 첫 사용과 실패 복구

### P0-1. 위험 한도 미설정을 오류가 아닌 설정 유도로 표시

- **화면**: `/` 대시보드 `확인 필요` 섹션, `/settings`
- **사용자 문제**: 포트폴리오를 만든 직후 두 화면 모두에
  `포트폴리오 위험 한도 정책이 설정되지 않았습니다.`가 빨간 오류 박스로 표시된다.
  사용자는 아무것도 잘못하지 않았는데 첫 화면이 고장난 것처럼 보인다.
- **원인**: `PortfolioRiskAlertService.getRiskAlerts()`가 `getRiskPolicy()`를 먼저 호출하고,
  정책이 없으면 `PortfolioRiskPolicyNotFoundException` → 404가 된다
  (`PortfolioService.java:65-74`). 프론트의 `getJsonResponse()`는 상태 코드를 버리고
  모든 비정상 응답을 `Error`로 던지므로(`apiError.ts:26-28`) 404와 500을 구분할 수 없다.
- **제안**: 404를 별도 상태로 다룬다. 위험 섹션은 적색 오류 대신 중립 안내 카드로
  `위험 한도를 설정하면 종목별 비중 초과를 확인할 수 있습니다` + `설정으로 이동` 링크를
  보여 준다. `/settings`도 동일하게 오류 대신 빈 폼과 안내 문구를 보여 준다.
- **필요 데이터**: 없음. HTTP 상태 코드만 프론트로 전달하면 된다.
- **현재 API로 가능한가**: **가능.** 백엔드 변경 불필요.
  `apiError.ts`가 `status`를 담은 오류 타입을 던지도록 바꾸면 된다.

### P0-2. 모든 조회 영역에 재시도 수단 제공

- **화면**: 전체 (`/`, `/holdings`, `/strategy-guides`, `/settings`)
- **사용자 문제**: 모든 페이지가 `useEffect`에서 한 번만 조회한다. 실패하면 오류 문구만
  남고 복구 수단이 없다. 시세 제공자는 429(`MarketDataRateLimitExceededException`),
  502(`MarketDataUnavailableException`, `StaleMarketDataException`)를 실제로 반환하며,
  전략 가이드는 종목 수만큼 외부를 호출하므로 가장 자주 실패하고 가장 가치가 큰 화면이다.
  이전 위험 경고 화면에 있던 `↻` 재조회 버튼이 라우팅 개편 과정에서 사라졌다.
- **제안**: 섹션 헤더 우측에 재조회 버튼을 되살린다. 조회 중에는 비활성화하고
  `aria-label`로 대상을 명시한다. 오류 카드 안에도 `다시 시도` 버튼을 둔다.
  429는 재시도를 유도하기보다 `요청 한도에 도달했습니다. 잠시 후 다시 시도해 주세요`로
  안내하고 버튼을 잠시 비활성화한다.
- **필요 데이터**: 없음.
- **현재 API로 가능한가**: **가능.** 백엔드 변경 불필요.

### P0-3. 포트폴리오 전환 시 이전 데이터 제거

- **화면**: 전체
- **사용자 문제**: 상단 포트폴리오 선택을 바꾸면 이전 포트폴리오의 평가금액·손익·보유
  종목이 화면에 그대로 남은 채 새 응답이 도착할 때 값만 바뀐다. 로딩 표시도 없다.
  **다른 포트폴리오의 금액을 현재 선택된 포트폴리오의 값으로 오인할 수 있다.**
- **원인**: `DashboardPage`의 `isValuationLoading` / `isAlertsLoading`은 최초 로드 후
  `false`가 되고 다시 `true`가 되지 않는다(`DashboardPage.tsx:18-19, 21-39`).
  `valuation`·`alerts`도 effect 진입 시 초기화하지 않는다.
  `HoldingsPage`는 `valuation`과 `error`를, `SettingsPage`는 `policy`·입력값·`error`·`success`를,
  `StrategyGuidesPage`는 `holdings`·`candidates`를 같은 방식으로 남긴다.
  특히 실패한 포트폴리오에서 정상 포트폴리오로 바꾸면 이전 오류 문구가 계속 보인다.
- **제안**: 조회 effect 진입 시 해당 영역의 데이터·오류·성공 메시지를 초기화하고
  로딩 상태로 되돌린다. 공통 조회 훅으로 묶어 네 페이지가 같은 규칙을 쓰게 한다.
  전환 중에는 값 자리에 스켈레톤 또는 `조회 중`을 표시해 빈 화면 점멸을 막는다.
- **필요 데이터**: 없음.
- **현재 API로 가능한가**: **가능.** 프론트 상태 관리 문제다.

### P0-4. 첫 사용 경로를 매매 기록 등록까지 연결

- **화면**: `/portfolios/new` → `/` → `/transactions/new`
- **사용자 문제**: 온보딩은 `생성 후 거래 기록을 등록하면 현재 평가와 위험 경고를 확인할 수
  있습니다`라고 안내하지만(`PortfolioOnboardingPage.tsx:47`), 생성 후 `/`로 이동하면
  **매매 기록 등록으로 가는 길이 화면에 없다.** 사이드바는 대시보드·보유 종목·전략 가이드·설정
  네 개뿐이고(`AppLayout.tsx:6-11`), `/transactions/new` 링크는 `/holdings`의 보조 버튼
  하나뿐이다(`HoldingsPage.tsx:15`). 데이터가 없는 사용자는 빈 대시보드에서 멈춘다.
- **제안**:
  - 사이드바에 `매매 기록`을 추가한다.
  - 보유 종목이 0개일 때 대시보드의 빈 상태를 안내 문구가 아니라 다음 행동 카드로 바꾼다:
    `아직 등록된 매매 기록이 없습니다` + `매매 기록 등록` 기본 버튼 + 위험 한도 설정 보조 링크.
  - 온보딩 성공 후 `/`가 아니라 `/transactions/new`로 보내는 선택지도 검토한다.
    (어느 쪽을 기본으로 할지는 제품 결정이므로 사용자 확인이 필요하다.)
- **필요 데이터**: `PortfolioValuationResponse.holdingValuations.length`
- **현재 API로 가능한가**: **가능.** 백엔드 변경 불필요.

## 3. P1 — 운영 신뢰성과 정보 밀도

### P1-1. 세션 만료를 로그인 화면으로 복귀시키기

- **화면**: 전체
- **사용자 문제**: `PortfolioProvider`는 마운트 시 한 번만 인증을 확인한다
  (`PortfolioProvider.tsx:19-43`). 이후 세션이 끊기면 각 페이지는 401/403을 일반 오류
  문자열로 표시하고, 앱은 `SignInPage`로 돌아가지 않는다. 사용자는 원인을 알 수 없는
  오류만 반복해서 본다. `AccessDeniedException` → 403도 마찬가지다.
- **제안**: `apiError.ts`가 상태 코드를 보존하고, 401은 인증 필요 상태로 승격해
  `SignInPage`를 보여 준다. 403은 `이 포트폴리오에 접근할 수 없습니다`로 구분해 표시한다.
- **필요 데이터**: 없음. 백엔드는 이미 401/403을 반환한다.
- **현재 API로 가능한가**: **가능.**

### P1-2. 전략 가이드에 추세·신호 이벤트와 기준일을 전면 배치

- **화면**: `/strategy-guides`
- **사용자 문제**: 카드는 기준 가격·기준일·전략 ID·최근 교차 후 주 수를 보여 주지만
  `trend`와 `signalEvent`를 표시하지 않는다(`StrategyGuideList.tsx:16`). 이 둘은
  판단의 근거가 되는 시장 사실이며 API가 이미 내려보내고 있다. 또한 기준일이 카드마다
  흩어져 있어, 장 시작 전에 `지금 보는 데이터가 언제 것인가`를 한눈에 알 수 없다.
  주봉 신호는 금요일 종가 이후 확정되므로 기준일은 이 화면의 가장 중요한 맥락이다.
- **제안**:
  - 카드에 추세(`장기 이동평균 위/아래`)와 신호 이벤트(`상향 교차`/`하향 교차`/`없음`)를
    텍스트 라벨로 추가한다. 색만으로 구분하지 않는다.
  - 페이지 상단에 기준일 배너를 둔다. `guides`의 `dataAsOf`가 모두 같으면 단일 날짜로,
    다르면 범위로 표기한다. **모두 같다고 가정하지 않는다.**
- **필요 데이터**: `decision.trend`, `decision.signalEvent`, `decision.metadata.dataAsOf`
- **현재 API로 가능한가**: **가능.** 세 필드 모두 응답에 있다.
  배치 응답 최상위 `dataAsOf` 요약 필드는 없지만, 클라이언트 계산으로 대체 가능하다.

### P1-3. 전략 응답의 null 가능 필드를 타입과 화면에 반영

- **화면**: `/strategy-guides`
- **사용자 문제**: `frontend/src/types/strategyGuide.ts:12-13`은 `trend`와 `signalEvent`를
  필수로 선언하지만, 백엔드 `StrategyDecisionResponse`의 4-인자 생성자는 `trend`,
  `signalEvent`, `weeksSinceCross`에 모두 `null`을 넣는다. 현재 화면은 `weeksSinceCross`만
  null을 검사한다. P1-2에서 `trend`를 표시하기 시작하면 null이 그대로 렌더된다.
- **제안**: 세 필드를 optional로 선언하고, 값이 없을 때는 해당 항목을 감추거나
  `정보 없음`으로 표시한다. `weeksSinceCross`의 `null`을 `0`으로 대체하지 않는다.
  `0`은 `이번 주 교차`라는 다른 의미다.
- **필요 데이터**: 없음.
- **현재 API로 가능한가**: **가능.** 프론트 타입 문제다.

### P1-4. 노출 비중 전체를 위험 화면에 노출

- **화면**: `/settings` 또는 새 위험 섹션
- **사용자 문제**: 현재 위험 정보는 한도를 **초과한** 종목만 보여 준다. `0건`이
  `비중이 여유 있다`인지 `한도에 거의 닿았다`인지 알 수 없다. 한도를 조정할 근거가 없다.
- **제안**: 위험 한도 편집 폼 아래에 종목별 현재 비중 목록을 두고, 각 행에 한도 대비
  위치를 막대로 표시한다. 초과 행만 적색으로 강조하고 나머지는 중립색을 쓴다.
- **필요 데이터**: `GET /api/members/{memberId}/portfolios/{portfolioId}/exposures`
  → `market`, `ticker`, `marketValue`, `exposureRate`
- **현재 API로 가능한가**: **가능. 단 현재 프론트엔드가 이 API를 전혀 호출하지 않는다.**
  백엔드는 구현되어 있고 소비처만 없다.

### P1-5. 종목 검색 입력의 요청 폭주·경쟁 상태·키보드 접근성

- **화면**: `/transactions/new`
- **사용자 문제**: `AssetSearchInput`은 입력이 바뀔 때마다 즉시 조회한다
  (`AssetSearchInput.tsx:17-29`). 디바운스가 없어 `AAPL` 입력에 4번 요청이 나간다.
  이전 요청을 취소하지 않으므로 느린 앞선 응답이 최신 결과를 덮을 수 있다.
  결과 목록은 `ul` 안의 버튼 나열이라 조합 상자(combobox) 시맨틱이 없고,
  화살표 키 이동과 결과 개수 안내가 없다. `.asset-search-results button`에는
  포커스 스타일도 정의되어 있지 않아(`App.css:218-231`) 키보드 사용자가 현재 위치를
  볼 수 없다. 조회 중 표시도 없다.
- **제안**: 250~300ms 디바운스, 최신 요청만 반영하는 순번 가드 또는 `AbortController`,
  `role="combobox"` + `aria-expanded` + `aria-activedescendant` + `role="listbox"/"option"`,
  화살표·Enter·Escape 처리, 결과 개수의 `aria-live` 안내, 선택 항목의 뚜렷한 포커스 링을 적용한다.
- **필요 데이터**: `GET /api/assets?market&query`
- **현재 API로 가능한가**: **가능.** 백엔드 변경 불필요.

### P1-6. 보조 텍스트 색상이 WCAG AA 대비를 만족하지 못함

- **화면**: 전체
- **사용자 문제**: 보조 텍스트 계층이 4.5:1 기준에 미달한다. 측정값:

  | 토큰 | 배경 | 대비 | 판정 |
  | --- | --- | --- | --- |
  | `.eyebrow`, `.section-label` `#73818e` (11px) | `#f5f7f8` | 약 3.7:1 | 미달 |
  | `.summary-grid small` `#81909a` (12px) | `#fff` | 약 3.3:1 | 미달 |
  | `.search-message` `#74828c` (12px) | `#fff` | 약 4.0:1 | 미달 |
  | `.page-header p` `#697786` (14px) | `#f5f7f8` | 약 4.3:1 | 경계 미달 |

  11px·12px는 WCAG의 large text(18.66px bold 또는 24px)에 해당하지 않으므로 4.5:1이 필요하다.
- **제안**: 보조 텍스트 계층을 한 단계 어둡게 조정한다(대비 4.5:1 이상 확보).
  `.eyebrow`는 11px를 유지하려면 더 어두운 값이 필요하고, 밝기를 유지하려면 크기를
  키워야 한다. 두 축 중 하나를 선택한다. 색상 값은 §5의 토큰 표에서 함께 제안한다.
- **필요 데이터**: 없음.
- **현재 API로 가능한가**: 해당 없음(스타일).

### P1-7. `KR` 시장 선택지가 지원되지 않는 상태로 노출됨

- **화면**: `/transactions/new`
- **사용자 문제**: 거래 등록 폼이 `한국 (KR)`을 선택지로 제공한다
  (`TradeTransactionEntryPage.tsx:71`). `Market` enum에도 `KR`이 있다. 그러나
  - 모든 금액은 `formatUsd()`로 렌더된다(`utils/format.ts:1-3`). 시장과 무관하게 `$`가 붙는다.
    KR 종목을 등록하면 원화 금액이 달러로 표시된다.
  - `TwelveDataMarketPriceProvider`는 티커를 그대로 `symbol`로 넘기며 시장 구분이 없다.
  - `asset_listings` 초기 데이터는 `asset_profiles`(Track A)에서 복제되므로 KR 종목이 없다.
  - `docs/PROJECT_CONTEXT.md:14`는 초기 대상 시장을 미국으로 규정하고,
    `docs/ARCHITECTURE_ROADMAP.md`에 KR 확장 계획이 없다.

  사용자가 KR을 고르면 등록은 되지만 평가 단계에서 실패하거나 잘못된 통화로 표시된다.
- **제안 (택일, 사용자 결정 필요)**:
  - (a) 시장 지원 범위가 정해질 때까지 폼에서 `KR` 선택지를 감춘다. 화면 변경만으로 끝난다.
  - (b) 통화를 데이터로 다룬다. 이 경우 §4-1의 계약 보완이 선행되어야 한다.

  **(a)를 권한다.** 현재 제품 범위와 일치하고 API 변경이 없다.
- **필요 데이터**: (a) 없음 / (b) §4-1 참조
- **현재 API로 가능한가**: (a) **가능**. (b) **불가 — 계약 보완 필요.**

### P1-8. 대시보드가 보유 종목 표를 통째로 반복

- **화면**: `/`
- **사용자 문제**: 대시보드가 `/holdings`와 동일한 `HoldingValuationList` 전체 표를 렌더한다
  (`DashboardPage.tsx:61`). 채택 설계는 `보유 종목의 짧은 현황`을 명시했다
  (`WEB_MVP_DESIGN.md:7`). 현재 구현은 페이지를 길게 만들고 `전체 보기` 링크의 의미를 없앤다.
  종목이 늘수록 위험 경고 섹션이 화면 아래로 밀려난다.
- **제안**: 대시보드에서는 평가금액 상위 5개만 요약 행으로 보여 주고, 나머지는
  `외 N개`와 `전체 보기`로 넘긴다. 표시 컬럼은 종목·평가금액·수익률로 줄인다.
  `/holdings`는 지금의 전체 표를 유지한다.
- **필요 데이터**: 기존 `holdingValuations`를 클라이언트에서 정렬·절단
- **현재 API로 가능한가**: **가능.**

## 4. P2 — 완결성과 유지보수

### P2-1. 매매 기록 조회 화면 (API 갭)

- **화면**: 신규 `/transactions`
- **사용자 문제**: 등록은 되지만 조회·검증 수단이 없다. 오타로 잘못 등록한 체결 내역을
  확인하거나 되짚을 방법이 화면에 없고, 보유 수량이 이상해도 원인을 추적할 수 없다.
- **제안**: 등록한 체결 내역을 최신순 목록으로 보여 준다. 시장·티커·매수/매도·수량·
  체결 단가·수수료·체결 시각을 표시한다. 수정·삭제는 이 제안의 범위가 아니다.
- **필요 데이터**: 포트폴리오의 체결 내역 목록.
- **현재 API로 가능한가**: **불가.** `POST .../transactions`만 존재한다
  (`TradeTransactionController`). 대응하는 조회 엔드포인트가 없다.
- **원하는 계약**: `GET /api/members/{memberId}/portfolios/{portfolioId}/transactions`가
  기존 `TradeTransactionResponse`(`id`, `market`, `ticker`, `tradeType`, `quantity`,
  `executedPrice`, `fee`, `tradedAt`)의 목록을 반환한다. **기존 DTO를 그대로 쓰면 되므로
  새 필드나 새 값을 만들 필요가 없다.** 정렬 기준과 페이지네이션 필요 여부는 Codex 판단.

### P2-2. 등록 시점의 종목 유효성 피드백

- **화면**: `/transactions/new`
- **사용자 문제**: 티커는 자유 입력이며 대문자로만 정규화된다
  (`TradeTransactionEntryPage.tsx:31`). 카탈로그에 없는 코드로 등록해도 즉시 통과하고,
  문제가 드러나는 시점은 한참 뒤 대시보드의 시세 조회 실패(502)다. 원인과 결과가 멀다.
- **제안**: 검색 결과에서 선택한 경우 표시명을 확정 칩으로 보여 준다. 직접 입력한 코드가
  카탈로그에 없으면 제출 버튼 위에 `카탈로그에 없는 종목입니다. 시세 조회가 실패할 수
  있습니다`를 경고로 표시하되 등록은 막지 않는다(채택 설계가 직접 입력을 허용한다).
- **필요 데이터**: `GET /api/assets?market&query`
- **현재 API로 가능한가**: **가능.**

### P2-3. 위험 경고 카드의 색 사용 정정

- **화면**: `/` 위험 섹션
- **사용자 문제**: `.risk-details dd`가 `현재 비중`과 `최대 비중`을 **모두** 경고 적색
  `#bd3028`으로 칠한다(`App.css:631-638`). 최대 비중은 사용자가 설정한 정책값이지
  위험 신호가 아니다. 무엇이 문제인지 시각적으로 구분되지 않는다.
- **제안**: 초과한 `현재 비중`만 적색으로 두고 `최대 비중`은 중립 텍스트색을 쓴다.
- **필요 데이터**: 없음.
- **현재 API로 가능한가**: 해당 없음(스타일).

### P2-4. 비율 단위 규칙의 명문화

- **화면**: 전체
- **사용자 문제**: API가 두 가지 비율 단위를 섞어 쓴다. 접미사가 유일한 단서다.
  - `~Ratio` = 0~1: `maxLossPerTradeRatio`, `maxSingleAssetExposureRatio`
  - `~Rate` = 0~100: `exposureRate`, `maxExposureRate`, `returnRate`, `totalReturnRate`

  프론트는 이에 맞춰 `formatRatio`(×100)와 `formatPercent`(그대로)를 나눠 쓴다
  (`utils/format.ts:5-11`). 지금은 정확하지만 규칙이 어디에도 기록되어 있지 않다.
  화면이 늘거나 Flutter 클라이언트가 붙으면 재발하기 쉽다.
- **제안**: 규칙을 `docs/PROJECT_CONTEXT.md`에 한 줄로 명문화한다. 필드명 통일은
  계약 변경이므로 별도 승인 사항이다.
- **현재 API로 가능한가**: 문서 작업. 이 검토의 허용 범위 밖이므로 Codex에 이관한다.

### P2-5. 스타일 유지보수

- `.eyebrow, .section-label`이 `color`와 `font-size`에 `!important`를 쓴다
  (`App.css:415-421`). 이 때문에 로그인 패널은 여백만 덮어쓰는 우회를 하고 있다
  (`App.css:33-35`). P1-6에서 색을 조정할 때 함께 제거한다.
- `.form-actions button`, `.onboarding-panel button`, `.asset-search-results button`,
  `.topbar-link`, `.section-link`, `.sign-in-button`(일부) 에 `:focus-visible` 규칙이 없다.
  §5의 컴포넌트 상태 표에 맞춰 공통 포커스 링을 적용한다.
- 색상 hex가 파일 전반에 직접 반복된다. §5의 토큰으로 추출하면 P1-6의 대비 수정이
  한 곳에서 끝난다.

## 5. 재사용 가능한 시각 방향 제안

현재 팔레트는 이미 일관적이다. **새로운 룩을 도입하지 않고 지금 값을 의미 기반 토큰으로
정리하는 것**이 이 제안의 취지다. 이름은 CSS에 종속되지 않게 지어 향후 Flutter
`ThemeData`에 같은 의미로 옮길 수 있게 한다.

### 5-1. 색 역할

| 역할 | 값 | 용도 |
| --- | --- | --- |
| `surface/canvas` | `#f5f7f8` | 앱 배경 |
| `surface/raised` | `#ffffff` | 카드·표·폼 |
| `surface/muted` | `#fbfcfc` | 사이드바, 표 헤더 |
| `border/default` | `#e0e7e6` | 카드·표 경계 |
| `border/strong` | `#c7d2d1` | 입력 필드 |
| `text/primary` | `#17232c` | 제목·금액 |
| `text/secondary` | `#4f5e6a` | 본문 |
| `text/muted` | **`#5e6c78`** (현재 `#73818e`에서 조정) | 라벨·보조 — P1-6 대비 확보 |
| `accent/primary` | `#167568` | 기본 버튼·활성 내비 |
| `accent/hover` | `#0e6157` | 호버 |
| `accent/subtle` | `#e4f1ee` | 활성 배경 |
| `focus/ring` | `#158476` | 포커스 링 (2px, offset 2px) |
| `status/positive` | `#13734f` | 평가이익 |
| `status/negative` | `#bd3028` | 평가손실·한도 초과 |
| `status/caution` | `#735615` / 배경 `#fffbef` | 조회 불가 |
| `status/neutral` | `#1c5d82` / 배경 `#e7f1f8` | 보유 유지 |

`text/muted` 값은 대비 기준을 만족시키기 위한 제안이며, 최종 값은 구현 시 실제 측정으로
확정한다.

### 5-2. 상태 색은 항상 텍스트를 동반한다

현재 구현은 이 규칙을 잘 지키고 있다(`action-badge`에 한글 라벨, `risk-state`에 `비중 초과`).
유지 조건으로 명문화한다. **`REDUCE`는 `StrategyDecisionMaker`가 현재 반환하지 않으므로
범례나 필터에 노출하지 않는다.** 배지 컴포넌트는 값을 처리하되 UI에서 홍보하지 않는다.

### 5-3. 타이포그래피 역할

| 역할 | 크기 / 굵기 | 비고 |
| --- | --- | --- |
| `display` | 32 / 700 | 페이지 `h1` |
| `title` | 21 / 700 | 섹션 `h2` |
| `metric` | 25 / 700 | 요약 카드 금액. `tabular-nums` |
| `body` | 14 / 400 | 본문·표 |
| `label` | 13 / 700 | 폼 라벨·`dt` |
| `caption` | 12 / 400 | 보조 설명 |
| `eyebrow` | 12 / 800, `letter-spacing 0.1em` | 현재 11px에서 상향 — P1-6 |

금액·비율·수량에는 예외 없이 `font-variant-numeric: tabular-nums`를 적용한다.
현재 표·카드·요약에는 적용돼 있으나 `.holding-table td`의 수량 셀 등 일부만 상속에
의존하므로 규칙으로 고정한다.

### 5-4. 간격 스케일

`4 · 8 · 12 · 16 · 20 · 28 · 42 · 64`의 8단계로 정리한다. 현재 값(`14`, `18`, `22`, `30`,
`34`, `38`, `46`)은 이 스케일로 반올림한다. 밀도는 지금 수준을 유지한다 — 운영 도구로서
적절하다.

### 5-5. 컴포넌트 상태

모든 상호작용 요소는 다음 다섯 상태를 정의한다.

| 상태 | 규칙 |
| --- | --- |
| 기본 | 위 토큰 |
| 호버 | `accent/hover` 또는 배경 한 단계 |
| 포커스 | `focus/ring` 2px, offset 2px — **예외 없이 모든 포커스 가능 요소** |
| 비활성 | `opacity 0.6`, `cursor: wait`(제출 중) / `not-allowed`(조건 미충족) |
| 로딩 | 버튼은 라벨 교체, 영역은 스켈레톤 |

데이터 영역은 **로딩 / 성공 / 빈 상태 / 오류 / 부분 실패** 다섯 가지를 모두 구분한다.
부분 실패는 전략 가이드 전용이며, 성공 목록과 `unavailableAssets`를 동시에 렌더한다
(현재 `StrategyGuideList`가 올바르게 처리하고 있다).

### 5-6. 반응형 기준

현재 900px·760px 두 지점을 세 구간으로 정리한다.

| 구간 | 레이아웃 |
| --- | --- |
| `≥ 1024px` 데스크톱 | 좌측 고정 내비 224px + 작업 영역. 요약 3열. 가이드 2열. 보유 종목 전체 표 |
| `760 ~ 1023px` 태블릿 | 좌측 내비 유지. 요약 3열. 가이드 1열. 표는 가로 스크롤(`min-width 850px`) |
| `< 760px` 모바일 | 상단 가로 스크롤 내비. 요약 1열. 표 → 카드 전환. 위험 카드 1열 |

모바일에서 보유 종목 카드가 반드시 유지할 항목은 **종목 · 수익률 · 평가금액**이다.
현재 `HoldingValuationList`의 카드가 이 기준을 만족한다.
데스크톱 표의 필수 컬럼은 **종목 · 평가금액 · 평가손익 · 수익률**이며, 나머지는
가로 스크롤로 접근한다.

Flutter 호환을 위해 이 구간 값과 색·타이포 역할은 웹 CSS가 아니라 **의미 이름으로
공유**한다. 픽셀 값이 아니라 역할 이름이 계약이다.

## 6. API 및 데이터 모델 질문 (Codex·사용자 승인 필요)

가격, 주문 동작, 손절 값, 증권사 연동, 투자 판단은 제안하지 않는다. 아래는 화면이
요구하는 데이터 계약 질문이다.

1. **매매 기록 조회 엔드포인트** (§P2-1). 기존 `TradeTransactionResponse`를 재사용하는
   목록 조회. 새 필드 없음. 정렬·페이지네이션 정책 결정 필요.
2. **통화 표현** (§P1-7(b)). `KR` 시장을 실제로 지원한다면 평가·노출 응답이 통화를
   식별할 수 있어야 하고, 서로 다른 통화의 금액을 합산한 `totalMarketValue`의 의미를
   정의해야 한다. **환율·환산 규칙은 제품 결정이므로 이 검토에서 제안하지 않는다.**
   KR을 지원하지 않기로 하면 이 질문은 소멸하고 §P1-7(a)로 끝난다.
3. **배치 응답의 기준일 요약** (§P1-2). `StrategyGuideBatchResponse` 최상위에
   기준일 요약 필드를 둘지 여부. 클라이언트 계산으로 대체 가능하므로 선택 사항이다.
4. **비율 단위 규칙의 기록 위치** (§P2-4). 문서화로 충분한지, 필드명을 통일할지.

## 7. 권장 구현 순서

```
1) apiError.ts 상태 코드 보존 + 공통 조회 훅
   → P0-1(404 분기) · P0-2(재시도) · P0-3(전환 초기화) · P1-1(401 복귀)의 공통 토대
2) P0-4 첫 사용 경로 (사이드바 + 빈 상태 CTA)
3) P1-6 대비 수정과 §5 토큰 추출 (이후 모든 화면 작업의 전제)
4) P1-2 · P1-3 전략 가이드 정보 보강
5) P1-8 대시보드 요약화 · P1-4 노출 비중
6) P1-5 검색 입력 · P1-7 시장 선택지 · P2 항목
```

1번을 먼저 하는 이유는 P0 네 건 중 세 건과 P1-1이 같은 지점(`apiError.ts`와 페이지
조회 로직)을 고치기 때문이다. 개별로 처리하면 네 페이지에 같은 수정이 반복된다.

**첫 구현 단위 권장**: 1)과 2)를 하나의 세로 슬라이스로 묶는다. 사용자가 확인 가능한
완결된 흐름(로그인 → 포트폴리오 생성 → 매매 기록 등록 → 대시보드에서 평가 확인)이
처음으로 끊김 없이 이어지고, 검증도 lint·build와 수동 브라우저 흐름으로 끝난다.
