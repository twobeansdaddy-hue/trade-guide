## 1. 개요 및 설계 배경

### 1.1 배경과 S6b의 위치
증권사 주문 이력 가져오기 슬라이스 S6은 원래 세 가지(조회 기간 상한, 서버 구간 분할, 중복 호출 보호)를 다루기로 계획되었으나, 2026-09-10 분리 합의에 따라 다음 순서로 나뉘었다.

1. **S6a (구현 완료)**:
   - 조회 기간 상한: 달력일 기준 최대 366일(`MAX_REQUESTED_RANGE_DAYS = 366`, 양 끝 포함)을 초과하면 증권사 호출 전 즉시 HTTP 400 거부.
   - 중복 호출 보호(`BrokerDuplicateCallGuard`): 같은 포트폴리오·동일 동작이 진행 중이면 HTTP 409(`BROKER_CALL_IN_PROGRESS`), 직전 호출 성공 후 5초 쿨다운 내 재요청 시 HTTP 429(`BROKER_CALL_COOLDOWN`) 반환.
   - 증권사 HTTP 클라이언트 타임아웃(Connect 5초, Read 10초) 설정으로 무기한 스레드 점유 방지.
2. **S6b (본 설계 대상)**:
   - **서버 구간 분할(Server-side Date Chunking)**: 366일 상한 내의 넓은 조회 구간을 30일 단위 창(Sub-window)으로 쪼개어 오래된 창부터 순차 조회하되, 제공자 호출 공유 예산(`MAX_PAGES = 50`, 약 5,000건 체결)을 소진하면 미완료 창을 안전하게 버리고 마지막으로 완결된 창의 종료일까지를 부분 커버리지(`coveredOrderedTo`)로 반환.
   - **불완전 이력 승인 정책(Incomplete-History Approval Policy)**: 요청한 전체 기간을 끝까지 다 읽지 못한 실행(`fullyCovered = false`)에 담긴 주문을 매매 원장에 그대로 승인할 것인가, 차단할 것인가, 혹은 어떤 안전 게이팅을 거쳐야 하는가에 대한 투자 원장 정합성 정책 및 화면 UX 수립.

### 1.2 UX 설계 목표
1. **사용자 오인 방지**: "내가 요청한 1년 중 어디까지 수집되었고, 어디가 누락되었는가"를 기술 용어(커서, 페이지 예산 등) 없이 직관적 타임라인과 시각적 진행 상태로 제공한다.
2. **원장 정합성 절대 수호**: 불완전 이력을 조용히 승인하여 이후 기간 체결이 누락되거나 평단가가 왜곡되는 사태를 차단하고, "남은 구간 이어받기" 흐름을 통해 완전한 이력을 구축하도록 유도한다.
3. **방어적 오류 및 쿨다운 피드백**: 5초 쿨다운(429), 진행 중 충돌(409), 30일 단일 창 초과(422), 366일 초과(400) 등 다양한 제약 상황에서 레이아웃 이동(Layout Shift) 없는 실시간 카운트다운과 안내를 제공한다.
4. **유기적인 문맥 연계**: 보유 종목 화면(`/holdings`)의 정합성 점검 결과 및 거래 내역에서 주문 이력 가져오기(`/broker-accounts#broker-order-imports`)로 자연스럽게 연결되는 진입로를 마련한다.
5. **모바일 360px 및 접근성 준수**: 소형 모바일 기기에서의 텍스트 가로 넘침 및 터치 불편을 해소하고, 스크린리더(ARIA)와 색각 이상 사용자를 배려한다.

## 2. 근거, 추정, 승인 필요 정책의 구분 (Ground Truth)

본 설계안은 기존 코드와 저장소 문서에서 검증된 **확정 근거(Evidence)**를 기반으로 하며, 검증되지 않은 가정을 사실로 취급하지 않는다. 설계안에 포함된 **추정(Assumptions)**과 의사결정권자(사용자 및 Codex)의 **승인이 필요한 결정(Decisions Requiring Approval)**을 명확히 분리한다.

### 2.1 기존 구현 및 백엔드 계약 확정 사실 (Evidence)
- **기간 상한 (E4)**: `BrokerOrderImportService.requireRange`가 `ChronoUnit.DAYS.between(orderedFrom, orderedTo) + 1 > 366`일 때 HTTP 400 `IllegalArgumentException`을 발생시킴.
- **호출 보호 (B2/D7)**: `BrokerDuplicateCallGuard`가 진행 중 요청에 409(`BROKER_CALL_IN_PROGRESS`), 5초 이내 재호출에 429(`BROKER_CALL_COOLDOWN`)를 반환함.
- **구간 분할 알고리즘 (B3 원안)**: 30일 분할 창, 공유 50페이지 예산, 창 단위 완료/폐기 원칙, `completedWindows == 0`일 때 `PAGE_LIMIT_EXCEEDED`(422) 발생.
- **백엔드 DTO 확장안**: `run.coverage: { fullyCovered: boolean, coveredOrderedTo: string | null, nextOrderedFrom: string | null }` (추가 전용 필드로 하위 호환성 유지).
- **승인 집계 모델 (S2)**: `BrokerOrderImportRunDetail`은 `items` 배열 없이 `approval: BrokerOrderImportApprovalAssessmentResponse`를 반환하며, `approvable: boolean`과 `blocker: BrokerOrderImportApprovalBlocker`로 사전 판정 결과를 제공함.
- **원장 반영 멱등성 및 보호**: `TradeTransaction` 테이블의 부분 유니크 인덱스로 중복 반영 차단, `BROKER_ORDER_HISTORY` 거래는 일반 매매 삭제 불가(409).
- **프론트엔드 에러 해석 구조**: `frontend/src/api/apiError.ts`의 `hasApiStatus(err, status)` 및 `hasApiErrorCode(err, code)`로 409, 429, 422, 400을 정밀하게 분기할 수 있음.

### 2.2 제품 및 운영 추정 (Assumptions)
- **개인 계좌의 거래 밀도 추정**: 개인 투자자가 단일 30일 창 안에서 5,000건(일평균 약 166건)을 초과하는 경우는 극단적인 초단타 매매 계좌에 한정되며, 일반적인 경우 30일 창 하나는 수 페이지 이내에서 조기 종료될 것이다.
- **부분 커버리지의 주요 원인**: 사용자가 1년(366일)에 달하는 최대 구간을 한 번에 조회할 때, 활발한 매매 이력으로 인해 3~6개월 지점에서 누적 50페이지 예산이 먼저 소진되는 시나리오가 주를 이룰 것이다.
- **스냅샷 대조와의 필연적 불일치**: `reconciliation`은 "내부 원장 시뮬레이션 수량"과 "현재 시점의 증권사 최신 스냅샷 수량"을 비교한다. 만약 2024-01-01부터 오늘(2024-12-31)까지를 요청했는데 2024-06-30까지만 부분 커버되었다면, 하반기 6개월간 매수/매도한 수량이 누락되어 **대조 결과는 높은 확률로 `MISMATCHED` 또는 `REPLAY_FAILED`가 될 것**이다.

### 2.3 승인 필요 핵심 결정 (Decisions Requiring Approval)

```
[결정 1: 불완전 이력 승인 정책]
┌────────────────────────────────────────────────────────────────────────┐
│  질문: 요청 구간을 끝까지 가져오지 못한 실행(fullyCovered=false)을      │
│        사용자가 매매 원장에 승인할 수 있도록 허용할 것인가?           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
           ┌────────────────────────┴────────────────────────┐
           ▼                                                 ▼
   [선택지 A: 엄격 차단 (권고)]                      [선택지 B: 조건부 허용]
   - blocker: PARTIAL_COVERAGE_INCOMPLETE 도입       - reconciliation=MATCHED인 경우에만
   - 원장 왜곡/초과매도 위험 원천 차단               - 강력 경고 모달 + 2단계 체크박스
   - "남은 구간 이어받기" 완료 후 승인 유도          - 미수집 구간 거래 부재 확약 후 승인
```

#### [결정 1] 불완전 이력(Partial Coverage)의 원장 반영 승인 게이팅 정책
- **권고안 (선택지 A - 엄격 차단, Strict Blocking)**:
  - `fullyCovered === false`인 실행은 원장 반영 승인을 원천 차단한다.
  - 신규 블로커 코드 `PARTIAL_COVERAGE_INCOMPLETE`를 백엔드/프론트엔드 공통 계약으로 도입한다.
  - **근거**: 매매 원장의 평단가와 잔여 수량은 체결의 시간순 누적에 절대적으로 의존한다. 중간 구간까지만 원장에 반영되고 이후 구간이 비어 있으면, 향후 사용자가 해당 종목을 매도할 때 원장에 잔고가 없어 `초과 매도(REPLAY_FAILED)`가 발생하거나 허위 수익률이 계산된다. 안전을 최우선으로 하는 Trade Guide의 제품 원칙에 부합한다.
- **대안 (선택지 B - 조건부 승인, Conditional Approval)**:
  - 만약 대조 결과가 `MATCHED`인 기적적인 경우(예: 수집 중단일 이후 오늘까지 계좌에 아무런 매매가 없었음)에 한해 승인을 열어주되, "미수집 잔여 기간에 추가 거래가 전혀 없었음을 확인했습니다"라는 2단계 명시적 동의 체크박스를 필수로 받는다.
  - 대조가 `MISMATCHED` 또는 `REPLAY_FAILED`이면 당연히 선택지 A와 마찬가지로 차단된다.

#### [결정 2] 분할된 다중 실행 간의 체인 연결(Chained Runs) UX 정책
- 백엔드 아키텍처는 개별 `createPreview` 호출마다 독립된 `BrokerOrderImportRun` 행을 생성한다.
- 서버가 백그라운드에서 자동으로 다음 구간을 연쇄 호출하는 방식(오토 체이닝)은 5초 쿨다운 제약 및 동기 HTTP 타임아웃 위험으로 인해 배제되었다.
- **채택 UX**: 사용자가 "남은 구간 이어받기" 버튼을 누르면 상단 입력 폼에 `nextOrderedFrom`부터 기존 `requestedOrderedTo`까지의 날짜가 자동으로 세팅되고 사용자 확인 하에 다음 조회를 실행하도록 한다.

## 3. 조회 기간 요청 (Date-Range Request) UX

사용자가 366일 상한 규정을 인지하지 못하고 임의의 날짜를 입력하여 서버의 400 Bad Request 에러를 마주하는 일이 없도록, 클라이언트 단에서 직관적인 폼 컨트롤과 사전 검증 피드백을 제공한다.

### 3.1 날짜 입력 폼 및 프리셋 확장

기존 프리셋(7일, 14일, 30일, 90일)을 실제 세무·연말정산 및 연간 투자 복기 패턴에 맞추어 개편한다.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 새 주문 이력 미리보기 생성                                                   │
│ [최근 7일] [최근 30일] [최근 90일] [최근 180일] [최근 1년 (365일)]          │
├─────────────────────────────────────────────────────────────────────────────┤
│ ┌─────────────────────────────┐    ┌─────────────────────────────┐          │
│ │ 주문 조회 시작일            │    │ 주문 조회 종료일            │          │
│ │ [ 2025-09-10             📅] │    │ [ 2026-09-10             📅] │          │
│ └─────────────────────────────┘    └─────────────────────────────┘          │
│ ℹ️ 선택 기간: 366일 (최대 허용 범위 366일 이내 ✓)                           │
│ ℹ️ 증권사는 체결일이 아닌 주문일(KST) 기준으로 조회하므로, 미국 정규장 시차를   │
│    감안해 실제 조회 시 앞뒤 2일(Boundary Padding)이 자동 확장됩니다.         │
│                                                                             │
│ [ 주문 이력 미리보기 조회 ]                                                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **프리셋 버튼 구성**:
  - `최근 7일` (기본값): 최근 단기 체결 확인용
  - `최근 30일`: 월간 결산 및 단일 윈도우 최적 구간
  - `최근 90일`: 분기별 원장 정리용 (약 3개 윈도우 분할 예상)
  - `최근 180일`: 반기 결산용 (약 6개 윈도우 분할 예상)
  - `최근 1년 (365일)`: 연간 최대 조회용 (종료일 기준 365일 전 자동 계산)

### 3.2 366일 상한 클라이언트 실시간 유효성 검증

사용자가 날짜 피커에서 시작일이나 종료일을 변경할 때마다 즉시 두 날짜 사이의 달력일 수(`Math.floor((to - from)/(1000*60*60*24)) + 1`)를 계산한다.

1. **정상 범위 (1일 ~ 366일)**:
   - 헬퍼 텍스트: `선택 기간: N일 (최대 허용 범위 366일 이내 ✓)` (차분한 녹색 텍스트)
   - 제출 버튼 활성화 유지.
2. **상한 초과 (367일 이상, 예: 400일)**:
   - 즉시 폼 필드 하단에 경고 피드백 박스 노출:
     > ⚠️ **조회 기간은 양 끝 날짜를 포함해 최대 366일까지 가능합니다.** (현재 선택: **400일**)
     > 증권사 호출 안정성을 위해 1년 단위로 나누어 조회해야 합니다.
   - **원클릭 빠른 보정 액션 제공**: `[종료일 기준으로 시작일을 366일 전(2025-09-10)으로 자동 조정]` 버튼 노출.
   - 제출 버튼 비활성화(`disabled={isSubmitting || isRangeExceeded}`).

## 4. 진행 및 부분 커버리지 상태 시각화 (Progress & Partial Coverage States)

서버가 50페이지 예산 소진으로 조회를 중단했을 때, 사용자가 "시스템 결함"으로 오해하지 않고 "안전하게 중간 지점까지 완료된 상태"임을 명확히 인지할 수 있는 시각적 UI를 구축한다.

### 4.1 응답 DTO 및 UI 상태 매핑

```typescript
// frontend/src/types/brokerOrderImport.ts 확장안
export type BrokerOrderImportCoverage = {
    fullyCovered: boolean;
    coveredOrderedTo: string | null; // null이면 fullyCovered === true
    nextOrderedFrom: string | null;  // fullyCovered === false일 때 coveredOrderedTo + 1일
};

export type BrokerOrderImportRun = {
    // 기존 필드 유지...
    coverage?: BrokerOrderImportCoverage;
};
```

### 4.2 실행 이력 목록 카드(Run History Card) 표시 개선

좌측/상단의 실행 목록 카드에서 해당 실행의 커버리지 완결 여부를 뱃지로 즉각 식별하도록 한다.

```
┌───────────────────────────────────────────────────────────────┐
│ 2024-01-01 ~ 2024-12-31                      [스테이징 완료]  │
│ [⚠️ 부분 수집: 120일 완료 / 잔여 246일]                       │
│ 반영 후보 450건 / 수집 500건                 대조: 수량 차이 │
│ 2026-09-10 14:30:15                                           │
└───────────────────────────────────────────────────────────────┘
```
- **완전 수집 (`fullyCovered: true`)**: 기존대로 스테이징 완료 뱃지만 노출하거나 `[전체 수집 완료]` 중립 칩 표시.
- **부분 수집 (`fullyCovered: false`)**: 주황색 경고 테마 칩 `[⚠️ 부분 수집: 120일 완료 / 잔여 246일]`을 최상단에 배치하여 클릭 전에도 불완전 실행임을 인지시킴.

```
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 컴포넌트 세부 명세:
1. **타임라인 바 (CSS Flex/Grid 구조)**:
   - 전체 바 폭: 100%
   - 완료 구간(`width: (120/366)*100%`): 솔리드 테마 컬러(`var(--accent-primary)` 또는 안전 녹색), 텍스트 "수집 완료 (120일)".
   - 잔여 구간(`width: (246/366)*100%`): 사선 빗금 패턴 배경(Stripe pattern) + 회색 테두리, 텍스트 "미수집 잔여 (246일)".
2. **친절한 중단 사유 안내**:

3. **"남은 구간 바로 이어받기" 원클릭 인터랙션**:
   - 클릭 시 이벤트:
     1. 상단 `새 주문 이력 미리보기 생성` 폼의 `orderedFrom`에 `coverage.nextOrderedFrom`("2024-05-01") 자동 주입.
     2. `orderedTo`에 기존 실행의 `requestedOrderedTo`("2024-12-31") 자동 주입.
     3. 상단 폼 위치로 스무스 스크롤 이동(`scrollIntoView({ behavior: 'smooth' })`).
     4. 제출 버튼에 즉시 포커스 이동 및 시각적 하이라이트 애니메이션(펄스 효과).

## 5. 안전 재시도, 쿨다운(429) 및 충돌(409) 에러 UX

증권사 연동 API는 외부 금융 기관 시스템 및 내부 가드와 결합되어 다양한 제약 오류를 반환한다. 모든 오류는 사용자가 다음에 취해야 할 행동을 명확히 제시해야 하며 화면 깜빡임이 없어야 한다.

### 5.1 오류별 사용자 경험 매트릭스

| HTTP 상태 | 백엔드 코드 | 발생 상황 | 화면 사용자 안내 문구 | UI 인터랙션 및 복구 가이드 |
| :--- | :--- | :--- | :--- | :--- |
| **429** Too Many Requests | `BROKER_CALL_COOLDOWN` | 5초 쿨다운 이내 재호출 시도 | "증권사 조회 요청이 너무 빠릅니다. 잠시만 기다려 주세요." | 조회 버튼 텍스트를 `[ N초 후 재시도 가능... ]` 카운트다운 타이머로 전환하고 비활성화. 0초 도달 시 자동 활성화. |
| **409** Conflict | `BROKER_CALL_IN_PROGRESS` | 동일 포트폴리오에서 조회가 이미 진행 중임 | "현재 다른 탭 또는 화면에서 증권사 주문 조회가 진행 중입니다." | 3초 후 상태 확인 버튼 제공. 중복 클릭 억제. |
| **422** Unprocessable | `PAGE_LIMIT_EXCEEDED` | 30일 단일 창에서도 50페이지(5,000건) 초과 (0개 창 완료) | "해당 30일 구간에 주문이 너무 많아(5,000건 초과) 조회가 중단되었습니다. 더 좁은 기간으로 나누어 조회해 주세요." | `[ 14일 단위로 기간 좁히기 ]` 빠른 보정 버튼 제공. |
| **400** Bad Request | (없음, `IllegalArgumentException`) | 366일 초과, 시작일 > 종료일 | "조회 기간은 양 끝 날짜를 포함해 최대 366일까지 가능합니다." | 폼 입력 단에서 사전 차단하며, 서버 응답 시 해당 필드 테두리 빨간색 하이라이트. |
| **409** Conflict (승인 시) | `RECONCILIATION_MISMATCH` / `REPLAY_FAILED` | 수량 불일치 또는 초과 매도 감지 | "보유 종목 대조를 통과하지 못해 원장에 반영할 수 없습니다." | 안전 차단 카드(`broker-order-blocked-card`) 노출 및 대조 표 점검 유도. |

### 5.2 429 쿨다운(5초) 실시간 카운트다운 인터랙션 상세

프론트엔드는 서버 응답 메시지("3초 후 다시 시도할 수 있습니다.") 또는 5초 기본값을 파싱하여 로컬 타이머를 구동한다.

```
[클릭 직후 429 수신]
  ▼
[버튼 비활성화]: "⏳ 4초 후 다시 조회할 수 있습니다..."
  ▼ (1초 경과)
[버튼 비활성화]: "⏳ 3초 후 다시 조회할 수 있습니다..."
  ▼ (1초 경과)
[버튼 비활성화]: "⏳ 2초 후 다시 조회할 수 있습니다..."
  ▼ (1초 경과)
[버튼 비활성화]: "⏳ 1초 후 다시 조회할 수 있습니다..."
  ▼ (타이머 종료)
[버튼 활성화 복귀]: "주문 이력 미리보기 조회" (정상 파란색 버튼 복원)
```
- **레이아웃 안정성 (Cumulative Layout Shift = 0)**:
  - 폼 피드백 영역(`broker-order-import-form-feedback`)의 최소 높이를 `min-height: 24px`로 고정하여 메시지가 나타나거나 사라질 때 하단 폼 버튼이 위아래로 덜컹거리지 않도록 방지한다.
- **스크린리더 배려**:
  - 매 초마다 화면 낭독기가 읽으면 소음이 되므로, 카운트다운 숫자는 시각적 텍스트로만 갱신하고, 타이머가 완전히 끝났을 때만 `aria-live="polite"`로 "이제 다시 조회할 수 있습니다"를 1회 공지한다.

## 6. 불완전 이력 승인 게이팅 정책 및 UI (Approval Gating)

### 6.1 불완전 이력 승인 차단 배너 (Strict Gating UI)

`fullyCovered === false`인 실행을 선택했을 때, 우측 하단의 원장 반영 승인 영역은 **승인 버튼이 비활성화된 안전 차단 배너**를 렌더링한다.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 🛑 원장 반영 승인 비활성 (불완전 이력 안전 차단)                            │
├─────────────────────────────────────────────────────────────────────────────┤
│ **요청하신 기간 중 일부 구간(2024-01-01 ~ 2024-04-30)만 수집된 상태입니다.** │
│                                                                             │
│ 이 상태로 매매 원장에 반영하면 이후 체결 내역이 누락되어 포트폴리오의      │
│ 보유 수량과 평단가가 실제와 다르게 왜곡될 위험이 있습니다.                  │
│                                                                             │
│ 안전한 원장 보존을 위해 **남은 구간(2024-05-01 ~ 2024-12-31)까지 조회를    │
│ 완료한 후** 원장에 반영해 주세요.                                           │
│                                                                             │
│ ┌─────────────────────────────────────────────────────────────────────────┐ │
│ │ [ 🚀 남은 구간 이어받기 조회 실행 → ]                                   │ │
│ └─────────────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6.2 신규 승인 블로커(`BrokerOrderImportApprovalBlocker`) 확장 제안

백엔드와 프론트엔드가 공유하는 승인 블로커 enum에 `PARTIAL_COVERAGE_INCOMPLETE`를 추가한다.

```java
public enum BrokerOrderImportApprovalBlocker {
    RUN_NOT_STAGED,
    RECONCILIATION_MISMATCHED,
    RECONCILIATION_REPLAY_FAILED,
    NO_STAGED_ITEMS,
    ALL_BEFORE_BASELINE,
    /** 신규 추가: 서버 구간 분할이 예산 소진으로 전체 기간을 끝까지 커버하지 못함 */
    PARTIAL_COVERAGE_INCOMPLETE
}
```
- **평가 우선순위**:
  1. `RUN_NOT_STAGED` (스테이징 실패)
  2. `PARTIAL_COVERAGE_INCOMPLETE` (부분 커버리지 발생)
  3. `RECONCILIATION_MISMATCHED` / `RECONCILIATION_REPLAY_FAILED` (보유 대조 및 재생 검증 실패)
  4. `NO_STAGED_ITEMS` (적격 주문 0건)
  5. `ALL_BEFORE_BASELINE` (개시 잔고 이전 체결 제외)

### 6.3 다중 분할 실행의 순차 승인 규칙 안내 (Sequential Approval Order)

만약 사용자가 이어받기를 통해 실행 2건을 확보한 경우:
- **실행 #1** (2024-01-01 ~ 2024-04-30): 과거 구간
- **실행 #2** (2024-05-01 ~ 2024-12-31): 최신 구간

> **원장 반영 불변식 규칙**:
> 매매 기록은 **과거 체결부터 순서대로 승인**되어야 한다. 만약 실행 #2를 먼저 승인하려 하면, 실행 #1의 매수 기록이 아직 원장에 없어 실행 #2의 매도 주문 시점에 **초과 매도(Replay Validation Failure, 409)**가 발생하여 시스템이 자동으로 거절한다.

**UI 가이드**:
- 실행 #2 상세 화면에서 시스템이 "동일 계좌의 과거 미승인 실행(#1)이 존재합니다"를 감지하면:
  - 안내 박스: `ℹ️ 과거 구간 주문 이력(실행 #1)이 아직 원장에 반영되지 않았습니다. 과거 실행을 먼저 승인해야 수량 계산 오류 없이 안전하게 반영됩니다.`
  - 바로가기 링크: `[실행 #1로 이동하여 먼저 승인하기]`

## 7. 화면 간 문맥 연계 배치 (Holdings & Broker Contextual Entry Placement)

Trade Guide 내에서 사용자가 증권사 연동 데이터를 검토해야 하는 순간은 크게 두 곳이다. 각 화면의 상황에 맞는 정밀한 딥링크(Deep Link)와 문맥 파라미터를 배치한다.

```
┌──────────────────────────┐                   ┌──────────────────────────────┐
│  보유 종목 화면           │                   │  연동 계좌 화면               │
│  (/holdings)             │                   │  (/broker-accounts)          │
├──────────────────────────┤                   ├──────────────────────────────┤
│                          │                   │                              │
│ [정합성 점검 결과]       │ ── 딥링크 이동 ──▶ │ [Step 5: Tab 2]              │
│ - 사유: 기간 외 거래     │   (추천 기간 주입) │ - 폼에 시작/종료일 자동 세팅 │
│                          │                   │ - 즉시 미리보기 조회 가능    │
│                          │                   │                              │
│ [매매 기록 목록]         │                   │                              │
│ - 증권사 연동 거래 확인  │ ◀── 승인 후 복귀 ─ │ [원장 반영 승인 완료]        │
│   (BROKER_ORDER_HISTORY) │   (원장 갱신 확인)│ - "보유 종목에서 확인" 버튼 │
└──────────────────────────┘                   └──────────────────────────────┘
```

### 7.1 `/holdings` (보유 종목 화면)에서의 진입점 설계

1. **보유 종목 정합성 점검(`BrokerReconciliationSection`)과의 유기적 연계**:
   - 점검 결과가 `OUT_OF_PERIOD_HISTORY`("조회 구간 외 거래 가능성")인 경우:
     - 기존: 단순 텍스트 링크 (`/broker-accounts#broker-order-imports`)
     - **개선안**: 증권사 스냅샷 시각(`syncedAt`)을 기준으로 누락되었을 가능성이 높은 추천 기간을 URL 쿼리 파라미터로 조합하여 전달.
     - 링크 형태: `/broker-accounts?tab=order-history&from=2024-01-01&to=2024-12-31#broker-order-imports`
     - 연동 계좌 화면 진입 시 해당 쿼리를 감지하여 주문 조회 폼에 날짜를 즉시 프리필(Pre-fill).
   - 점검 결과가 `UNAPPROVED_RUN_EXISTS`("미승인 주문 이력 존재")인 경우:
     - 액션 링크: `[최근 조회된 주문 이력(실행 #${runId}) 검토 및 승인하기 →]`
     - 클릭 시 해당 실행이 선택된 상태로 `/broker-accounts#broker-order-imports` 열람.
2. **매매 이력 리스트(`TransactionHistoryList`) 내 증권사 거래 표시**:
   - `TradeTransactionSource`가 `BROKER_ORDER_HISTORY`인 행:
     - 파란색 전용 뱃지 `[증권사 연동: 토스증권]` 부여.
     - 일반 수동 매매와 달리 `[삭제]` 버튼을 숨기고, `[가져오기 내역]` 링크를 배치하여 `/broker-accounts`의 해당 실행 감사 카드로 이동 유도 (불필요한 409 삭제 차단 에러 사전 방지).

### 7.2 `/broker-accounts` (연동 계좌 화면)에서의 출구 및 후속 동선

1. **Step 4 (보유 종목 비교) → Step 5 Tab 2 (주문 이력 검토) 전환**:
   - 4단계 비교에서 수량 불일치(`QUANTITY_MISMATCH`)가 확인되면, 하단에 바로 "최근 체결 이력을 가져와 수량을 맞추시겠습니까?" 가이드 배너와 함께 `[주문 이력 검토 탭으로 이동]` 버튼 제공.
2. **원장 반영 승인 완료 후 `/holdings` 복귀 CTA**:
   - 승인 확인 모달이 성공하고 감사 카드가 활성화되었을 때, 성공 알림 메시지 바로 옆에 **[보유 종목 화면에서 업데이트된 잔고 확인하기 →]** 버튼을 제공하여, 사용자가 본인의 작업 결과를 즉각 체감할 수 있도록 동선을 완성한다.

## 8. 반응형(360px ~ 1280px) 및 웹 접근성(A11y) 설계

`docs/design/BROKER_ACCOUNTS_UX_AUDIT.md`에서 실측된 모바일 360px 환경의 가로 넘침(Horizontal Overflow) 및 61,000px 스크롤 피로도를 원천 해결하는 반응형 레이아웃 규칙과 접근성 기준을 수립한다.

### 8.1 360px 모바일 레이아웃 최적화


### 8.2 웹 접근성 (WCAG 2.1 AA) 준수 명세

1. **색상 단독 의존 배제 (Color-blind Friendly)**:
   - 커버리지 프로그레스 바의 완료 구간과 잔여 구간은 단순 녹색/회색 색상 차이뿐만 아니라, **사선 빗금 패턴(CSS Repeating Linear Gradient)**과 명확한 텍스트 레이블("완료 120일", "미수집 246일")을 반드시 함께 렌더링한다.
   - 대조 상태 뱃지도 색상 칩과 함께 상태 텍스트("수량 일치", "수량 차이", "스냅샷 없음")를 항상 병기한다.
2. **스크린리더(ARIA) 속성 설계**:
   - 커버리지 프로그레스 바:
     ```html
     <div
       role="progressbar"
       aria-valuenow="120"
       aria-valuemin="0"
       aria-valuemax="366"
       aria-valuetext="총 366일 중 120일 수집 완료, 잔여 246일 미수집"
       tabIndex={0}
     >
       ...
     </div>
     ```
   - 승인 차단 배너: `role="region" aria-label="원장 반영 승인 불가 안내"`
   - 폼 피드백 및 쿨다운 알림: `aria-live="polite"`
3. **키보드 접근성 (Keyboard Navigability)**:
   - 모든 프리셋 버튼과 딥링크는 키보드 `Tab` 키로 논리적 순서에 따라 이동 가능해야 함.
   - 승인 확인 모달 열림 시 포커스 트랩(Focus Trap) 적용 및 `Escape` 키로 안전 취소 지원.

## 10. 요약 및 승인 요청 사항

본 설계안은 S6b의 기술적 알고리즘(30일 창 분할, 50페이지 예산)을 사용자가 이해하기 쉬운 **시각적 커버리지 타임라인**으로 승화시키고, 불완전 이력이 원장을 오염시키지 않도록 **엄격 차단 및 이어받기 흐름**을 확립하는 것을 골자로 한다.

### 의사결정권자 확인 요청:
1. **[결정 1 승인 요청]**: `fullyCovered === false`인 실행에 대해 원장 반영 승인을 원천 차단하고 `PARTIAL_COVERAGE_INCOMPLETE` 블로커를 적용하는 권고안(선택지 A)을 채택하는 것에 동의하는가?
2. **[결정 2 승인 요청]**: 다중 분할 실행 간 오토 체이닝 대신 사용자가 직접 확인하며 진행하는 "남은 구간 이어받기(원클릭 폼 프리필)" 흐름을 채택하는 것에 동의하는가?

승인이 완료되면 위 P0 -> P1 -> P2 순서에 따라 프론트엔드와 백엔드 작업 계약을 분리하여 안전하게 구현을 전개한다.
